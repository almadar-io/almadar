في لعبة إرم، يجمع اللاعبون شظايا مدارية — أجزاء من السلوك تتراكب معًا لخلق قدرات جديدة. جهّز الدفاع والترميم معًا، وتتجدد دروعك أسرع بمقدار 1.5 ضعف. جهّز التعطيل والتصنيع، وتُلحق فخاخك ضررًا في منطقة.

هذه ليست مجرد آلية لعب. إنها نمط هندسة برمجية يحل الجدل بين الخدمات المصغرة والتطبيق المتجانس.

## مشكلة التركيب

هندسة البرمجيات عالقة بين خيارين سيئين:

**التطبيق المتجانس:** كل شيء في قاعدة شيفرة واحدة. سهل البناء، مستحيل التوسعة. كل تغيير يخاطر بكسر شيء غير متعلق.

**الخدمات المصغرة:** كل شيء في خدمته الخاصة. سهل التوسعة، مستحيل التنسيق. كل ميزة تتطلب تنظيم 5 خدمات و3 طوابير رسائل ودعاء.

كلا النهجين يعامل السلوك كمشكلة *موقع*: أين تعيش الشيفرة؟

السؤال الحقيقي هو: كيف *يتركب* السلوك؟

## دروس من تصميم الألعاب

في إرم، لعبة أكشن RPG للزنزانات مبنية على المدار، تُحدَّد شخصية اللاعب من خلال **أي المدارات يُجهّزها**:

| المدار | السلوك |
|--------|--------|
| **الدفاع** | امتصاص الضرر، توليد الدروع |
| **الترميم** | الشفاء بمرور الوقت، إزالة تأثيرات الحالة |
| **التعطيل** | مقاطعة الأعداء، تطبيق الإضعافات |
| **التصنيع** | إنشاء الفخاخ، بناء الأبراج |
| **الاستكشاف** | كشف الخريطة، اكتشاف الأعداء المخفيين |
| **التحويل** | تحويل الموارد، ترقية المعدات |
| **القيادة** | تقوية الحلفاء، تنسيق الإجراءات الجماعية |
| **الأرشفة** | تسجيل أنماط الأعداء، كشف نقاط الضعف |

كل مدار هو آلة حالة مكتفية ذاتيًا. الدفاع لا يعرف عن الترميم. الاستكشاف لا يعرف عن التصنيع.

لكن عندما تُجهّزها معًا، **يظهر سلوك ناشئ**.

## الرنين: التركيب يخلق الظهور

عندما تُجهَّز مدارات متوافقة في وقت واحد، تخلق **رنينًا** — تأثيرات تآزرية لا يُعرّفها أي مدار بمفرده:

```json
{
  "resonance": [
    {
      "requires": ["Defend", "Mend"],
      "effect": "Shield regeneration rate increased by 1.5x",
      "multiplier": { "shieldRegen": 1.5 }
    },
    {
      "requires": ["Disrupt", "Fabricate"],
      "effect": "Traps apply disruption debuffs",
      "multiplier": { "trapDamage": 1.3 }
    },
    {
      "requires": ["Archive", "Command"],
      "effect": "Allies receive enemy weakness intel",
      "multiplier": { "allyDamage": 1.2 }
    }
  ]
}
```

الرؤية الجوهرية: **لا يتغير أي مدار**. الدفاع ليس لديه شيفرة لـ "اعمل بشكل أفضل مع الترميم." الرنين هو خاصية *التركيبة*، وليس الأفراد.

هذا بالضبط كيف يجب أن يعمل تركيب البرمجيات.

## النمط: تركيب المدار

في المدار، تتواصل المدارات عبر **الأحداث**. كل مدار يُصرّح بما يُطلقه وما يستمع إليه:

```json
{
  "name": "DefendOrbital",
  "traits": [{
    "name": "ShieldTrait",
    "emits": ["SHIELD_ACTIVATED", "SHIELD_DEPLETED"],
    "stateMachine": {
      "states": [
        { "name": "Ready", "isInitial": true },
        { "name": "Active" },
        { "name": "Cooldown" }
      ],
      "transitions": [
        {
          "from": "Ready",
          "to": "Active",
          "event": "ACTIVATE_SHIELD",
          "effects": [
            ["set", "@entity.shieldHp", "@entity.maxShieldHp"],
            ["emit", "SHIELD_ACTIVATED"]
          ]
        },
        {
          "from": "Active",
          "to": "Cooldown",
          "event": "SHIELD_BROKEN",
          "effects": [
            ["set", "@entity.shieldHp", 0],
            ["emit", "SHIELD_DEPLETED"]
          ]
        }
      ]
    }
  }]
}
```

```json
{
  "name": "MendOrbital",
  "traits": [{
    "name": "HealTrait",
    "listens": [
      { "event": "SHIELD_DEPLETED", "triggers": "EMERGENCY_HEAL" }
    ],
    "stateMachine": {
      "transitions": [
        {
          "from": "Idle",
          "to": "Healing",
          "event": "EMERGENCY_HEAL",
          "effects": [
            ["set", "@entity.hp", ["+", "@entity.hp", ["*", "@entity.maxHp", 0.2]]]
          ]
        }
      ]
    }
  }]
}
```

**الدفاع** يُطلق `SHIELD_DEPLETED`. **الترميم** يستمع إليه. عندما يُكسر الدرع، يبدأ الشفاء تلقائيًا. لا يشير أي مدار إلى الآخر بالاسم. يتواصلان عبر ناقل الأحداث.

هذا يعني:
- **ترابط فضفاض** — الدفاع يعمل بدون الترميم
- **قابلية التركيب** — أضف الترميم ويظهر سلوك جديد
- **قابلية التحقق** — المُصرِّف يتحقق أن كل `emit` له `listen`
- **قابلية الاكتشاف** — اقرأ تصريحات الأحداث لفهم التفاعلات

## الآثار على هندسة البرمجيات

هذا النمط يترجم مباشرة إلى برمجيات الأعمال:

### التجارة الإلكترونية: معالجة الطلبات

```
OrderOrbital         PaymentOrbital         InventoryOrbital
    │                     │                      │
    ├─ emits:             ├─ listens:            ├─ listens:
    │  ORDER_PLACED       │  ORDER_PLACED        │  PAYMENT_CONFIRMED
    │                     │  → PROCESS_PAYMENT   │  → RESERVE_STOCK
    │                     │                      │
    │                     ├─ emits:              ├─ emits:
    │                     │  PAYMENT_CONFIRMED   │  STOCK_RESERVED
    │                     │  PAYMENT_FAILED      │  OUT_OF_STOCK
```

ثلاثة مدارات. كل منها مكتفٍ ذاتيًا. التركيب عبر الأحداث. المُصرِّف يتحقق من اكتمال رسم الأحداث — لا رسالة تمر بدون معالجة.

قارن هذا بنسخة الخدمات المصغرة:
- ثلاث خدمات، ثلاث عمليات نشر، ثلاث قواعد بيانات
- طابور رسائل (Kafka/RabbitMQ) لربطها
- طوابير الرسائل الميتة للرسائل الفاشلة
- أنماط الملحمة للمعاملات الموزعة
- مراقبة وتنبيهات لكل خدمة

نسخة المدار تُصرَّف إلى نشر واحد بنفس البنية المدفوعة بالأحداث، لكن بدون أعباء البنية التحتية.

### التعاون الجماعي: التطوير المتوازي

لأن المدارات تتواصل فقط عبر الأحداث، يمكن للفرق العمل بالتوازي:

- **الفريق أ** يبني مدار الطلب
- **الفريق ب** يبني مدار الدفع
- **الفريق ج** يبني مدار المخزون

يتفقون على عقود الأحداث:
```json
{
  "event": "ORDER_PLACED",
  "payload": {
    "orderId": "string",
    "items": "array",
    "total": "number"
  }
}
```

ثم يبنون بشكل مستقل. المُصرِّف يتحقق من تطابق العقود عندما تُركَّب المدارات.

## المكتبة القياسية: سلوكيات جاهزة

المدار يتضمن 11 سلوكًا في المكتبة القياسية تُدمج في أي مشروع:

| السلوك | ماذا يفعل |
|--------|-----------|
| `std/Loading` | حالات التحميل مع معالجة النجاح/الخطأ |
| `std/Fetch` | جلب بيانات غير متزامن مع إعادة المحاولة |
| `std/Submit` | إرسال النماذج مع التحقق |
| `std/Retry` | منطق إعادة المحاولة بتراجع أسي |
| `std/Poll` | أنماط الاستطلاع الطويل |
| `std/Pagination` | ترقيم الصفحات بمؤشر/إزاحة |
| `std/Search` | بحث نص كامل مع تصفية |
| `std/Sort` | فرز متعدد المفاتيح |
| `std/GameCore` | حلقة اللعبة الأساسية (تحديث، عرض) |
| `std/UnitBehavior` | سلوكيات الوحدات الذكية (دورية، حراسة، هروب) |
| `std/Inventory` | إدارة مخزون اللعبة |

استوردها في أي مدار:

```json
{
  "uses": [{ "from": "std/Pagination", "as": "Paginate" }],
  "traits": [
    { "ref": "Paginate.traits.PaginationTrait" },
    { "ref": "TaskInteraction" }
  ]
}
```

قائمة المهام الخاصة بك الآن لديها ترقيم صفحات. بدون كتابة شيفرة. مجرد تركيب.

## لماذا تفهم الألعاب هذا بشكل صحيح

الألعاب فهمت التركيب منذ الأزل. شخصية RPG هي تركيب من:
- الفئة (محارب، ساحر، متسلل)
- المعدات (سيف، درع، عصا)
- المهارات (كرة نار، شفاء، تسلل)
- التقويات/الإضعافات (مسموم، مبارك، مُسرَّع)

كل منها سلوك مكتفٍ ذاتيًا. معًا، يخلقون شخصية فريدة ذات قدرات ناشئة.

البرمجيات التجارية يجب أن تعمل بنفس الطريقة:
- **الفاتورة** هي تركيب من عمليات CRUD + الموافقة + توليد PDF + إشعار بالبريد الإلكتروني
- **المستخدم** هو تركيب من المصادقة + الملف الشخصي + التفضيلات + سجل النشاط
- **لوحة المعلومات** هي تركيب من المخططات + الفلاتر + التحديثات الفورية + التصدير

كل سلوك هو مدار. التركيب عبر الأحداث. المُصرِّف يضمن صحة التوصيل.

## الخلاصة

الجدل بين الخدمات المصغرة والتطبيق المتجانس يسأل السؤال الخاطئ. السؤال ليس أين يعيش السلوك. بل كيف يتركب السلوك.

المدارات تمنحك:
- **وحدات مكتفية ذاتيًا** (كالخدمات المصغرة) — كل مدار يملك آلة حالته
- **تركيب سهل** (كالتطبيق المتجانس) — استورد، ركِّب، صرِّف
- **توصيل مُتحقق منه** (لا يوفره أي منهما) — المُصرِّف يتحقق من كل اتصال حدث
- **سلوك ناشئ** (كالألعاب) — تأثيرات رنين من التركيبات المتوافقة

في المرة القادمة التي تصمم فيها نظامًا، لا تبدأ بـ "كم عدد الخدمات؟" ابدأ بـ "ما السلوكيات التي أحتاجها، وكيف تتركب؟"
