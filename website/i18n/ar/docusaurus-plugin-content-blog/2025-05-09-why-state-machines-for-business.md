فريق التطوير لديك يُطلق الميزات بسرعة. لكن الأخطاء تعود باستمرار. عمليات النشر تتعطل أيام الجمعة. قاعدة الكود تنمو، وكذلك الخوف من لمسها.

المشكلة ليست في فريقك. المشكلة في البنية.

<!-- truncate -->

## التكلفة الخفية لـ"تحرك بسرعة واكسر الأشياء"

تنفق صناعة البرمجيات ما يُقدّر بـ**2.41 تريليون دولار سنويًا** على إصلاح الكود السيئ (CISQ 2022). ليس على بناء ميزات جديدة. على *إصلاح ما هو موجود بالفعل*.

معظم هذه التكلفة تأتي من سبب جذري واحد: **حالة غير متوقعة**.

```
User clicks "Submit" →
  Is the form valid? (depends on 12 boolean flags)
  Is the user authenticated? (check a global variable)
  Is the network available? (hope for the best)
  Has this already been submitted? (add another boolean)
```

كل علامة منطقية (boolean flag) تُضاعف عدد الحالات الممكنة. مع 10 علامات، تطبيقك لديه **1,024 حالة ممكنة**، معظمها لم يختبره أحد.

## ماذا لو كان تطبيقك لا يمكن أن يكون إلا في حالات حددتها أنت؟

هذا ما تمنحك إياه آلة الحالة.

بدلاً من العلامات المنطقية المتناثرة والحالة الضمنية، تُعلن بالضبط ما هو ممكن:

```json
{
  "states": [
    { "name": "Draft", "isInitial": true },
    { "name": "Submitted" },
    { "name": "UnderReview" },
    { "name": "Approved" },
    { "name": "Rejected" }
  ]
}
```

خمس حالات. ليس 1,024. كل انتقال بينها صريح:

```json
{
  "from": "Draft",
  "to": "Submitted",
  "event": "SUBMIT",
  "guard": ["and",
    ["not-empty", "@entity.title"],
    ["not-empty", "@entity.description"]
  ]
}
```

الحارس يقول: لا يمكنك الإرسال بدون عنوان ووصف. هذه ليست مكتبة تحقق قد تنسى استدعاءها. إنها **بنية تفرض القاعدة**.

## الحجة التجارية

### 1. الأخطاء تصبح مستحيلة معماريًا

في التطبيق التقليدي، تمنع الأخطاء بالاختبارات. الاختبارات تغطي الحالات التي *فكرت فيها*. آلات الحالة تمنع الأخطاء بجعل الحالات غير الصالحة *غير قابلة للتمثيل*.

نافذة منبثقة لا يمكن إغلاقها؟ مُصرِّف المدار يرفضها:

```
Error: CIRCUIT_NO_OVERLAY_EXIT
  State 'EditModal' renders to 'modal' slot but has no exit transition.
  Users will be stuck in this overlay.
```

هذا الخطأ يُطلق في *وقت التصريف*. قبل النشر. قبل ضمان الجودة. قبل المستخدمين.

### 2. سرعة التطوير تزداد

مع المدار، تطبيق كامل — واجهة أمامية، واجهة خلفية، قاعدة بيانات، واجهة برمجية — يُصرَّف من ملف مخطط واحد:

```bash
orbital compile invoice-app.orb --shell typescript -o app/
```

تطبيق CRUD نموذجي يستغرق 2-4 أسابيع تقليديًا يستغرق **أيامًا** بنهج المخطط أولًا. الكود المُولَّد يتعامل مع التوجيه، وإدارة الحالة، ونقاط API، ونماذج قاعدة البيانات.

### 3. الامتثال يصبح تلقائيًا

للصناعات المنظمة، المخطط *هو* المواصفة:

```json
{
  "from": "InProgress",
  "to": "Completed",
  "event": "COMPLETE",
  "guard": ["and",
    ["=", "@entity.allFieldsFilled", true],
    [">=", "@entity.inspectorSignatures", 2]
  ]
}
```

لا يمكن للمفتش إكمال تقرير بدون ملء جميع الحقول وتوقيعين. هذا ليس اقتراحًا في دليل تدريب. إنه مفروض من قبل النظام.

المدققون لا يحتاجون مراجعة الكود. يراجعون المخطط — مستند JSON قابل للقراءة *هو* النظام.

### 4. التأهيل يستغرق ساعات، لا أسابيع

المطورون الجدد لا يحتاجون فهم آلاف الأسطر من React و Express و Redux. يقرأون المخطط:

- **الكيانات** تخبرهم ما هي البيانات الموجودة
- **الحالات** تخبرهم ما يمكن للتطبيق فعله
- **الانتقالات** تخبرهم كيف ينتقل بين الحالات
- **الحرّاس** يخبرونهم بقواعد العمل
- **التأثيرات** تخبرهم ما يحدث عند كل انتقال

المخطط هو التوثيق. وهو دائمًا دقيق لأنه *هو* النظام الذي يعمل.

## مثال واقعي: نظام تفتيش حكومي

بنينا نظام تفتيش ميداني للاستخدام الحكومي. النهج التقليدي: 6 أشهر، 5 مطورين، إدارة سير عمل معقدة.

مع المدار:

- **5 مراحل تفتيش** مُمثّلة كحالات (المقدمة، المحتوى، التحضير، التسجيل، الختام)
- **المتطلبات القانونية** مُشفّرة كحرّاس (لا يمكن الإغلاق بدون جميع الحقول الإلزامية)
- **سجل المراجعة** مدمج في آلة الحالة (كل انتقال يُسجّل)
- **توليد المستندات** يُطلق كتأثيرات عند انتقال الختام

المخطط 400 سطر. يُولّد تطبيق ويب كاملًا مع واجهة برمجية خلفية، ونماذج قاعدة بيانات، وواجهة مستخدم للمفتشين.

## متى لا تناسب آلات الحالة

آلات الحالة ليست لكل شيء:

- **مواقع المحتوى الصرف** (المدونات، صفحات الهبوط) — لا حالة معقدة
- **البرامج النصية لمرة واحدة** — لا تستحق الهيكل
- **النماذج الأولية الاستكشافية للغاية** — أحيانًا تحتاج اكتشاف ما تبنيه أولًا

لكن لـ**أي تطبيق به سير عمل، نماذج، موافقات، عمليات متعددة الخطوات، أو أدوار مستخدمين** — وهو معظم برمجيات الأعمال — آلات الحالة تقضي على فئات كاملة من الأخطاء.

## الخلاصة

السؤال ليس ما إذا كانت آلات الحالة تستحق التعلم. السؤال هو هل تستطيع تحمل الأخطاء التي ستُطلقها بدونها.

المدار يجعل آلات الحالة عملية لتطبيقات الأعمال:
- ملف مخطط واحد → تطبيق كامل المكدس
- منع الأخطاء في وقت التصريف → حوادث إنتاج أقل
- مخططات قابلة للقراءة → مراجعات وتأهيل أسرع
- حرّاس وانتقالات → الامتثال ككود

مستخدموك لن يعرفوا أنهم يستخدمون آلة حالة. سيلاحظون فقط أن الأشياء تعمل.

مستعد لتجربتها؟ اطلع على [دليل البدء](/docs/getting-started/introduction).
